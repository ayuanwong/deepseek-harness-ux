# Agent Note：运行中过程详情不能带动背后的会话

Status: implemented

[English](2026-08-14-live-process-scroll-containment.md) | 中文

## 问题

一段 Windows 长任务录屏暴露了两套滚动所有权同时处理同一手势。“运行详情”被限制为 230px 并在内部滚动，但一次较大的滚轮增量可能先完成内层移动，再把余量交给会话滚动容器。与此同时，技术行新增或被替换时，Chromium 原生滚动锚定会调整位置，而 ChatView 自己的锚点账本与 ResizeObserver 也会恢复吸底。

可见故障并不是普通的多余内边距。过程行和输入区会先一起向上移动，在视口下方留下大段空白；后续实时输出又可能把它们突然拉回底部。输入区确实 sticky 在正确宿主中，但宿主的位置已经被两套竞争机制带走。

## 决策

限高的技术日志独占纵向滚轮输入。一个非 passive 监听器会统一像素、行与整页增量，只更新日志自身的 `scrollTop`，在上下边界截断，并阻止浏览器把任何余量交给会话。没有形成内部滚动的已结算详情不拦截手势。CSS 同时把运行日志声明为 `overscroll-behavior-y: none` 边界，使触控与 compositor 驱动路径共享同一约束。

会话滚动容器声明 `overflow-anchor: none`。吸底、分页锚点、用户滚动归因与输入区尺寸修正已经由 ChatView 负责；原生锚定在这里是第二个写入者，并非后备。滚动容器会封闭边界 overscroll；常驻会话根也显式使用 `min-height: 0` 与 100% 高度上限接受 flex 收缩，避免平台间 min-content 差异把整列撑出框架。

输入区继续 sticky 在权威会话滚动容器内部。把它搬成独立 fixed 图层的方案被否决：那会改变输入区上滚轮、问题／审批接管，以及既有的单滚动容器约定，却仍没有消除竞争的锚点写入者。

## 考虑过的替代方案

**允许限高日志在边缘继续滚动链。** 否决，因为一次较大的滚轮手势仍会推动过程详情背后的对话，重新产生已报告的跳动。

**在 ChatView 的锚点账本旁继续保留浏览器原生锚定。** 否决，因为实时行高度变化时，两个独立的位置所有者无法提供稳定的吸底约定。

**把输入区移到单独的 fixed 图层。** 否决，因为这会改变输入区上的滚轮行为、问题／审批接管和既有的单滚动容器约定，同时没有移除相互竞争的会话锚点。

## 后果

- 滚动很长的实时技术日志不会再改变 transcript 位置；要滚动 transcript，指针需要离开这个限高区域。
- 实时技术行增加与展开项尺寸变化只由 ChatView 的位置账本处理，输入区始终位于滚动容器底部，不会进入空白尾部。
- 已结算详情继续作为普通不限高内容流，不会截留滚轮输入。
- Agent 输入、Tool 策略、会话事件与模型 token 路径均不变化；本次只改浏览器展示。

## 测试

`chat-view.client.spec.tsx` 向可滚动的运行中详情区域发送像素与整页滚轮增量，验证非 passive 监听器在本地消费并截断滚动。

`chat-scroll-contract.e2e.ts` 在组装后的真实浏览器中构造很长的运行中技术区域，验证内层移动时会话 `scrollTop` 不变、输入区底边仍与滚动容器底边对齐、原生锚定已关闭，且 document 不会长出视口之外。
